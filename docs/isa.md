# cyber-spine 指令集与运行时规范

状态：设计冻结（fuel 除外，见 §7）
适用范围：字节码编码、寄存器与变量、指令语义、时钟、任务模型、后端接口

---

## 0. 用途与非目标

### 0.1 它做什么

cyber-spine VM 只做两件事：

| 动词 | 指令 | 含义 |
|---|---|---|
| **探查** | `FSENSE` / `ISENSE` | 读取外部肌肉的当前状态，供闭环反馈 |
| **激发** | `FEXCITE` | 向外部肌肉送出激发值 |

其余一切都是在这两个动词之间做计算。**闭环反馈只能通过 `YIELD` 表达**（§6.9）——后端在虚拟时间轴上的时刻不可观测，`WAIT` 表达不了"等到被控对象响应"。

### 0.2 系统形式

```
S_n          = observe(M_n)                 # 探查：被控对象当前状态
T_{n+1}, E_n = VM(T_n, S_n, dt)             # 激发：任务推进 + 贡献产出
M_{n+1}      = Backend(M_n, E_n, dt)        # Rust 后端，VM 不碰
```

`M` 是完全的黑盒：VM 不持有它的状态，也不持有它的前向模型。**被控对象可替换**（廉价仿真 / 真实皮套 / 录制的 sensor 轨迹）是这套划线的核心收益：先用仿真训练，再部署到真模型，程序一行不改。

### 0.3 非目标

以下全部**不在 VM 内**，且这是有意为之：

| 非目标 | 归属 |
|---|---|
| 物理引擎、渲染器 | 后端 |
| 约束求解器 | 后端辅助库 |
| 冲突裁决（多个激发如何合并） | 后端（肌肉定义） |
| 数值净化、范围钳制 | 后端（辅助库可提供标准实现） |
| 动作选择、调度、串联 | VM 之上的层 |
| rig 格式、资源管线 | 外部工具 |
| 被控对象状态与前向模型 | 后端 |

最后一条是硬边界：如果控制器需要前向模型（"我这么做脸会变成什么样"），它必须把模型编进自己的变量和代码里。把前向模型放进 VM 就等于把皮套知识放回 VM。

### 0.4 核心不变量

1. 指令流只出现 bind 期解析过的整数；皮套相关的名字只存在于头段。
2. 指令集的全部副作用只有三处：**寄存器、任务变量、任务的命令值**。
3. 一个任务是一条协程：**挂起点只有 `YIELD` 和 `WAIT`**。
4. **VM 只搬运，不解释。** 激发值原样送达后端；冲突裁决、钳制、净化都是后端的事。
5. 字段宽度 = 寄存器文件长度，索引按构造合法，零运行期边界检查。
6. 一切越界在**加载期**验证，一切超限在**运行期确定性失败**。不存在"尽力而为"。

## 1. 编码

### 1.1 指令格式

**定长 8 字节**，逻辑上是 `u64`：

```
 63..56   op     8
 55..50   rd     6    ┐
 49..44   ra     6    │ 6 位 ⇒ 每个寄存器文件恰好 64 项
 43..38   rb     6    │ 字段宽度 = 数组长度 ⇒ 无需边界检查
 37..32   rc     6    ┘
 31..0    imm   32    opcode 决定其解释
```

`8 + 6 + 6 + 6 + 6 + 32 = 64`，无填充位。

定长带来的性质：指令下标 ↔ 字节偏移是 `×8`；跳转目标天然落在指令边界上；程序镜像可整体随机访问；bind 期重定位是一遍顺序扫描。

### 1.2 `imm` 的解释

`imm` 不是通用字段，含义由 opcode 决定：

| 解释 | 使用的指令 |
|---|---|
| f32 位模式 | `FMOVI`、`WAIT` |
| i32 | `IMOVI` |
| 无符号索引 | sensor / var / muscle 下标 |
| 有符号跳转偏移 | `JMP`、`IJZ`、`IJNZ`、`FLT`…`INE` |
| 未使用 | 无 `imm` 语义的指令（必须填 0） |

### 1.3 跳转偏移约定

```
target = pc + 1 + off        off = imm as i32
```

- 单位是**指令数**，不是字节数。
- 相对**下一条**指令。
- `off = 0` 表示跳到紧邻的下一条。
- `off < 0` 表示后向跳转（循环）。

> **差一错误警告**：`pc + 1` 这个约定在源码层完全不可见，写错会让程序里所有跳转同时偏一条指令。偏移计算必须实现在**唯一一个共享函数**里，汇编器与反汇编器都调用它，并有往返测试。

### 1.4 字节序与序列化

- 内存表示为 `u64`（宿主字节序）；磁盘/网络表示固定为**小端 8 字节**。
- 程序镜像自包含：无常量池、无外部符号表（标签已在汇编期解析）。

## 2. 寄存器与变量

### 2.1 两个寄存器文件

```rust
pub struct Regs {
    pub f: [f32; 64],   // f0..f63
    pub i: [i32; 64],   // i0..i63
}
```

opcode 决定操作数索引哪个文件（`FADD` 走 `f`，`IADD` 走 `i`），因此不需要文件选择位。

**为什么 f32 而不是 f64**：整条流水线都是 f32。用 f64 会让每条 `FEXCITE` 前都要插转换指令，且与"每指令 4 个寄存器字段"的编码争夺空间。需要精确性的场合本来就该用整数寄存器。

**为什么整数文件必需**：时序逻辑——延迟、相位、状态机、渐变计时——用 f32 计数会在长时间运行后出现比较失败。定时与计时的基准是**虚拟周期**（§6），不是秒。

**为什么恰好 64 个**：6 位字段的可表达范围就是 0..63。让**编码宽度等于数组长度**，索引按构造不可能越界，于是不需要边界检查分支，更不需要掩码——掩码会把越界索引**静默别名**到合法寄存器，制造极难定位的 bug。

需要更多活跃值时，正确出路是**溢出到任务变量**（§2.4），而不是扩大寄存器窗口。

### 2.2 硬连零

`f0` 恒为 `0.0`，`i0` 恒为 `0`。**对它们的写被静默丢弃。**

它们承担具体职责：

- `FGT ra, f0, L` / `FLT ra, f0, L` —— 免费的"判正 / 判负"，也是浮点判真的唯一写法（本 ISA 故意没有浮点相等比较）。
- `FCLAMP rd, ra, f0, rb` —— 最常用的钳制形态之一。
- `ISUB rd, i0, ra` —— 整数取负。

### 2.3 生命周期：任务级

> **寄存器在任务创建时清零，此后随挂起与恢复存活，直到任务结束。**

语义是：**寄存器的生命周期就是任务的生命周期。**

挂起时必须**整块保存**寄存器（约 520 字节/任务）。ISA 里没有"语句"这个概念，无法要求挂起点没有活跃临时值；整块保存是唯一安全且简单的做法，代价可忽略。

推论：**没有任何寄存器跨任务存活。** 任务之间在寄存器层面完全隔离。

### 2.4 任务变量

```rust
pub struct Vars {
    pub f: Box<[f32]>,
    pub i: Box<[i32]>,
}
```

- 长度与初值由**头段声明**，任务创建时一次分配。
- 作用域是**任务局部**，随任务结束消亡。
- 浮点变量与整数变量是**两个独立 id 空间**，各自 0 基址。
- **没有全局变量**（见 §12）。

**长期存在的状态 = 长期存在的任务。** 呼吸、待机摆动、心情演化都是永不 `HALT` 的任务，与短动作并发。这样 VM 里不存在跨任务的可变共享状态，也就不存在"谁来裁决全局写入"的问题。

由此得到一个很实在的性质：

> **任务之间除了肌肉贡献和 sensor 之外没有任何交互通道。一个任务的行为完全由 `(自身状态, sensor 快照)` 决定。**

所以任何单个动作都能拿一段合成的 sensor 轨迹离线测试，不需要其他任务在场。

**例外只有一处**：同一 tick 内任务共享**周期预算**（§6.5），因此"某任务是否超预算 fault"可以依赖同 tick 内其他任务的周期消耗。变量层面依然完全隔离；重放按 `TaskId` 顺序整场进行即可复现。

## 3. 全局语义

**G1 寄存器。** `f0..f63` 为 IEEE-754 binary32，`i0..i63` 为 i32。`f0`/`i0` 硬连零，写丢弃（§2.2）。

**G2 寄存器生命周期。** 任务创建时清零，随挂起/恢复存活，随任务结束消亡（§2.3）。

**G3 执行模型。** 单线程顺序执行。`pc` 从单元入口开始，每次执行一条指令后 `pc += 1`，除非该指令是跳转或挂起。**挂起点只有 `YIELD` 与 `WAIT`。**

执行由**虚拟时钟**驱动，量纲是**周期**（§6）。一个 tick 结束于所有到期任务都推进到挂起 / `HALT` / fault 之后（§8.4）。

**G4 浮点。** 一律 IEEE-754 binary32，round-to-nearest-even。**禁止 FMA 收缩**（`a*b+c` 不得被宿主编译成融合指令）。**禁止 flush-to-zero**，非规格化数必须保留——FTZ 会破坏跨平台重放。

**G5 浮点比较。** 按 IEEE 语义，**任一操作数为 NaN 时比较结果为假**（不跳转）。本 ISA 故意不提供浮点相等比较：浮点 `==` 是 bug 温床，NaN 还让它不可全序。需要比较用 `FSUB + FABS + FLT` 配容差（§12）。

**G6 算术不 trap。** 整数运算回绕（二进制补码）。浮点运算产生 NaN/±Inf 并继续传播。算术本身永远不产生 fault。

**G7 sensor 快照。** 全部 sensor 在每个 tick 开始时**一次性采样**，整 tick 冻结：同一 tick 内所有任务看到同一份快照，重复读同一 sensor 结果相同。首个 tick 全为 0。

快照只在 tick 边界采样。host 可能在一个显示帧内推进多次 tick（§6.6），因此一个 tick 内发生的多次恢复，看到的仍是同一份快照。

由此：**任务在同一次恢复中读不到自己刚送出的激发值**——那要等后端推进之后。这保证了 VM 与被控对象之间**没有代数环**，是 tick 良定义的前提。

**G8 id 只出现在 `imm`。** id 绝不进入寄存器。这是零运行期边界检查的前提。

**G9 确定性。** 给定相同的任务状态、相同的 sensor 快照、相同的 `dt`、相同的 fuel 策略、相同的任务创建顺序、相同的周期计费表版本，VM 产出的激发流逐位可复现。

`dt` 取自头段声明的时钟，是常数（§6.1），不由宿主提供，因此宿主的调度抖动不进入 VM。周期计费表属于程序语义，是重放记录的组成部分（§6.3）。

> **这个保证只覆盖 VM。** 后端是否确定（物理摆动、平台数学库差异）是后端的性质，不在 VM 的承诺范围内。重放记录的是**激发流 + sensor 快照**；要重放位姿，前提是后端本身确定。

**G10 激发语义：保持。** `FEXCITE` 设定任务对某肌肉的命令值，**该值一直保留到被再次改动**。没有"每帧重置为中性"，也没有"未被提及即归零"——那都是后端根据自身语义决定的事。

**G11 并发与顺序。** 多个任务并发运行，顺序敏感的一切都按**任务创建顺序**（`TaskId` 递增）裁定：任务的恢复顺序、贡献列表的排列顺序都是如此。

**G12 fault 语义。** 任何 fault 都表示：**该任务立即终止并被移除**，其全部贡献随之消失，fault 记录 `(task_id, pc, 原因)`。同样输入必须死在同一条指令上。

"超限"包含两种情况：fuel 耗尽（§7）与 tick 周期预算耗尽（§6.5）。

fault 的任务贡献消失是刻意的：fault 是 bug 信号，视觉上的跳变**应该**被看见，而不是被静默抹平。

## 4. 指令表

全部 **48 条**。记法：`rd/ra/rb/rc` 为 6 位寄存器号，文件由 opcode 决定。

### 4.1 传送与常量（0x00）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x00 | `FMOVI` | `rd, imm` | `f[rd] = f32::from_bits(imm)` |
| 0x01 | `IMOVI` | `rd, imm` | `i[rd] = imm as i32` |
| 0x02 | `FMOV` | `rd, ra` | `f[rd] = f[ra]` |
| 0x03 | `IMOV` | `rd, ra` | `i[rd] = i[ra]` |

`FMOVI` 是**位精确**嵌入，不经过数值转换，因此可嵌入 NaN、±Inf、非规格化数与任意字面量。汇编器负责字面量 → 位模式的转换。

### 4.2 浮点二元（0x10）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x10 | `FADD` | `rd, ra, rb` | `f[rd] = f[ra] + f[rb]` |
| 0x11 | `FSUB` | `rd, ra, rb` | `f[rd] = f[ra] - f[rb]` |
| 0x12 | `FMUL` | `rd, ra, rb` | `f[rd] = f[ra] * f[rb]` |
| 0x13 | `FDIV` | `rd, ra, rb` | `f[rd] = f[ra] / f[rb]` |
| 0x14 | `FMIN` | `rd, ra, rb` | NaN 传播极小；`FMIN(±0, ∓0) = -0.0` |
| 0x15 | `FMAX` | `rd, ra, rb` | NaN 传播极大；`FMAX(±0, ∓0) = +0.0` |

`FMIN`/`FMAX` 采用 **NaN 传播**而非"忽略 NaN 取另一个"：NaN 一旦出现就保持可见。带符号零的取值也必须写死，否则跨平台重放不一致。

### 4.3 浮点一元（0x20）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x20 | `FNEG` | `rd, ra` | 翻转符号位（对 NaN 与 ±0 同样成立） |
| 0x21 | `FABS` | `rd, ra` | 清符号位 |
| 0x22 | `FSQRT` | `rd, ra` | IEEE 平方根；`ra < 0` → NaN；`FSQRT(-0.0) = -0.0` |
| 0x23 | `FSIN` | `rd, ra` | `sin(ra)`，弧度 |
| 0x24 | `FCOS` | `rd, ra` | `cos(ra)`，弧度 |
| 0x25 | `FFRAC` | `rd, ra` | `ra - floor(ra)`；有限值结果 ∈ [0,1)；NaN/±Inf → NaN |

**`FSIN`/`FCOS` 必须由 VM 自带实现**（固定范围规约 + 固定多项式），**不得转调平台 libm**——libm 最后几位在不同平台/版本上会差，跨平台重放会静默漂移。范围规约的迭代次数必须固定，不得随输入变化（§6.2）。

**`FFRAC` 存在的原因是振荡器的相位累加器**：f32 尾数 24 位，不回绕的相位在约 1.6×10⁴ 个周期后精度损失会变成可见抖动。需要 `floor(x)` 时用 `FSUB rd, ra, rfrac` 得到，不单独设 `FFLOOR`。

### 4.4 浮点三元（0x30）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x30 | `FMADD` | `rd, ra, rb, rc` | `f[rd] = f32(f32(f[ra]*f[rb]) + f[rc])` |
| 0x31 | `FLERP` | `rd, ra, rb, rc` | `t = f32(f[rb]-f[ra]); u = f32(t*f[rc]); f[rd] = f32(f[ra]+u)` |
| 0x32 | `FCLAMP` | `rd, ra, rb, rc` | `f[rd] = FMIN(FMAX(f[ra], f[rb]), f[rc])` |

**`FMADD` 不是融合乘加**，是两次舍入。理由：融合需要宿主有硬件 FMA 才能位精确。将来真需要融合时**新增 `FFMA`**，绝不重定义 `FMADD`——程序是持久化的，重定义会悄悄改变已有策略的行为。

`FLERP` 的求值顺序写死在语义里（先减、再乘、再加）。它**不对 `rc` 做 [0,1] 钳制**，允许外推。

`FCLAMP` 定义为 `FMIN(FMAX(x,lo),hi)` 的复合，因此 `rb > rc` 时结果为 `rc`。

### 4.5 整数与转换（0x40）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x40 | `IADD` | `rd, ra, rb` | 回绕加 |
| 0x41 | `ISUB` | `rd, ra, rb` | 回绕减 |
| 0x42 | `IMUL` | `rd, ra, rb` | 回绕乘 |
| 0x43 | `ITOF` | `rd, ra` | `f[rd] = f32(i[ra])`，超 2²⁴ 丢精度 |
| 0x44 | `FTOI` | `rd, ra` | 向零截断；NaN/±Inf → 0；越界饱和到 `i32::MIN`/`MAX` |

`F2I` 的三个边界行为（截断方向、非有限值、饱和）必须写死——任何一条留空都会变成平台差异。

### 4.6 控制流（0x50）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x50 | `JMP` | `imm` | `pc = pc + 1 + off` |
| 0x51 | `IJZ` | `ra, imm` | `i[ra] == 0` → 跳转 |
| 0x52 | `IJNZ` | `ra, imm` | `i[ra] != 0` → 跳转 |
| 0x53 | `FLT` | `ra, rb, imm` | `f[ra] < f[rb]` → 跳转 |
| 0x54 | `FLE` | `ra, rb, imm` | `f[ra] <= f[rb]` |
| 0x55 | `FGT` | `ra, rb, imm` | `f[ra] > f[rb]` |
| 0x56 | `FGE` | `ra, rb, imm` | `f[ra] >= f[rb]` |
| 0x57 | `ILT` | `ra, rb, imm` | 有符号 `<` |
| 0x58 | `ILE` | `ra, rb, imm` | 有符号 `<=` |
| 0x59 | `IGT` | `ra, rb, imm` | 有符号 `>` |
| 0x5A | `IGE` | `ra, rb, imm` | 有符号 `>=` |
| 0x5B | `IEQ` | `ra, rb, imm` | `==` |
| 0x5C | `INE` | `ra, rb, imm` | `!=` |

不跳转时 `pc += 1`。详见 §5。

### 4.7 输入（0x60）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x60 | `FSENSE` | `rd, imm` | `f[rd] = sensors_f[imm]` |
| 0x61 | `ISENSE` | `rd, imm` | `i[rd] = sensors_i[imm]` |

两个**独立的 id 空间**，各自 0 基址。头段声明的 sensor 按类型归入对应空间，汇编器把名字解析成 `(类型, 下标)` 并选择 opcode。

**肌肉自动注册为同名浮点 sensor**，于是读回自己刚设定的值（实际上是后端推进后的值）是最常见形态：

```
FSENSE  r0, mouth_open     # 读当前值
FEXCITE mouth_open, r1     # 写新的命令值
```

预声明内置 sensor：

| 名称 | 类型 | 含义 |
|---|---|---|
| `dt` | f32 | 固定步长 = `1 / hz`，常数（§6.1） |
| `tick` | i32 | 已推进的 tick 数（§6.4） |

### 4.8 挂起（0x70）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x70 | `YIELD` | — | 挂起到下一个 tick，恢复时从下一条指令继续 |
| 0x71 | `WAIT` | `imm` | 挂起 `f32::from_bits(imm)` 秒，恢复时从下一条指令继续 |

两条指令都会先推进 `pc` 再挂起，所以恢复点是它们的下一条指令。寄存器与任务变量跨挂起存活。

`WAIT` 的时长按 `dt` 换算成 tick 数：`wake_at = now + ceil(seconds / dt)`。`dt` 是常数（§6.1），因此这个换算不受宿主调度影响。

`imm` 必须是非负有限 f32，且**不超过头段声明的 `max_wait`**（加载期验证，§10）。加上界的原因见 §6.7。

`WAIT 0` 的 `ceil(0/dt) = 0`，语义等同于 `YIELD`。

**`WAIT` 是开环定时，不是等待条件**（§6.9）。"阻塞直到条件成立"不需要新指令——`YIELD` 加已有的条件跳转与 `JMP` 就够了：

```
L:  FSENSE  r0, smile
    FGT     r0, r_thresh, L_done
    YIELD                    # 条件未成立：本 tick 到此为止，让后端推进
    JMP     L
L_done:
```

反馈必然落后至少一个 tick（G7 + G10），这是 VM 与被控对象之间没有代数环的另一面。

一个既不 `HALT` 也不挂起的循环会一直跑到 fuel 耗尽，产生确定性 fault（§7）。这是刻意的：无限循环是 bug，必须被抓住。

### 4.9 任务变量（0x90）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x90 | `FVGET` | `rd, imm` | `f[rd] = vars_f[imm]` |
| 0x91 | `FVSET` | `imm, ra` | `vars_f[imm] = f[ra]` |
| 0x92 | `IVGET` | `rd, imm` | `i[rd] = vars_i[imm]` |
| 0x93 | `IVSET` | `imm, ra` | `vars_i[imm] = i[ra]` |

变量随任务结束消亡。需要跨动作存活的量请用**永不 `HALT` 的任务**（§2.4）。

### 4.10 激发（0x80）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0x80 | `FEXCITE` | `imm, ra` | `values[imm] = f[ra]; set_mask.set(imm)` |

**纯搬运，不做任何数值处理。** 不钳制、不净化、不合并——三者都是后端的事（§9）。

值一直保留到被再次改动（G10）。

### 4.11 杂项（0xA0）

| 编码 | 助记符 | 操作数 | 语义 |
|---|---|---|---|
| 0xA0 | `HALT` | — | 任务完成，"动作执行完成" |
| 0xA1 | `NOP` | — | 无操作 |

binder 在单元末尾补 `HALT`。执行越过单元末尾 = 加载期验证失败，不可能是运行期状态。

### 4.12 汇总

```
0x00  4   FMOVI  IMOVI  FMOV  IMOV
0x10  6   FADD  FSUB  FMUL  FDIV  FMIN  FMAX
0x20  6   FNEG  FABS  FSQRT  FSIN  FCOS  FFRAC
0x30  3   FMADD  FLERP  FCLAMP
0x40  5   IADD  ISUB  IMUL  I2F  F2I
0x50 13   JMP  IJZ  IJNZ  FLT  FLE  FGT  FGE
          ILT  ILE  IGT  IGE  IEQ  INE
0x60  2   FSENSE  ISENSE
0x70  2   YIELD  WAIT
0x80  1   FEXCITE
0x90  4   FVGET  FVSET  IVGET  IVSET
0xA0  2   HALT  NOP
```

其余编码保留，未使用字段必须填 0（bind 期校验）。

## 5. 控制流与标签

### 5.1 相对偏移

跳转一律使用**相对偏移**：`target = pc + 1 + off`，单位是指令数，`off` 为 i32。前向与后向都允许。

- **收益**：可重定位代码片段。片段内部的跳转整块搬到任何基址都仍然正确，只有跨越片段边界的跳转需要 fixup。
- **代价**：位置依赖；在跳转跨越的范围内插入或删除指令会使该跳转失效。控制流图可能有环，**指令数无法静态界定**，因此依赖 fuel 作为运行期上界（§7）。
- **运维纪律**：**标签是唯一的可编辑表示**。变异、组合、打补丁均作用于带标签的源码，编码后的偏移是派生产物。已 bind 的镜像视为**冻结产物**，不做原地偏移字节补丁——要改就重新汇编。

### 5.2 汇编期标签解析

源语言中控制流以标签或结构化构造表达；`ELSE`/`END`/`WHILE` 之类是**汇编器伪指令**，lowering 到 `JMP` + 条件跳转 +（需要时）`YIELD`，不占 opcode。ISA 因此保持 48 条。

```
第一遍（收集）
  pc = 0
  for item in source:
      if item is label: labels[name] = pc      # 标签指向其后的第一条指令
      else:             pc += 1
  code_len = pc

第二遍（发射）
  pc = 0
  for item in source:
      if item is label: continue
      if item is jump with target t:
          off = labels[t] - (pc + 1)
          check(off 装进 i32)
          emit(op, off as i32)
      else:
          emit(...)
      pc += 1
```

### 5.3 校验（汇编 / bind 期）

1. 引用的标签必须已定义。
2. 跳转目标必须在当前单元 `[0, code_len]` 内，其中 `code_len` 是 binder 追加的隐式 `HALT`——使"跳到末尾"这一合法惯用法可用。
3. `off` 能装进 i32（等价于 `code_len < 2³¹`）。
4. 目标必然落在指令边界上（定长编码的构造性保证）。

### 5.4 挂起与循环

"等待"有两种形态，区别是**开环 vs 闭环**（§6.9）：

| 形态 | 性质 | 写法 | 用途 |
|---|---|---|---|
| 定长等待 | **开环**：按虚拟时钟排节目 | `WAIT 0.3` | 保持一段时间 |
| 条件等待 | **闭环**：等被控对象 | `L: 计算条件; 条件成立则跳出; YIELD; JMP L` | 闭环反馈 |

**判据：只要条件里出现 sensor 的当前值，就必须走条件等待（`YIELD`）。**

周期性行为（呼吸、待机摆动）用**永不终止的任务**表达：

```
L:  FSENSE  r0, tick
    ...     计算相位与波形
    FEXCITE breath, r0
    WAIT    0.033
    JMP     L
```

周期任务用 `WAIT` 是正确的：它按虚拟时钟排节目，不等待被控对象。这里的 `FSENSE tick` 只是取相位基准，不是在等条件成立。

### 5.5 调试信息

标签表与 `指令下标 → 源行号` 的 line_map 存放于**独立 debug section，不进入可执行镜像**。反汇编因此可显示 `JMP L_blink_end` 而非 `JMP +37`，而编码本身不为可读性付出代价。

## 6. 时钟与时间

执行流由**虚拟时钟**驱动，量纲是**周期**。指令处在被时钟驱动的执行流里，因此必然占据一个确定的周期数——这不是谁分配的额度，也不可协商。时间是这个计数的派生量。

### 6.1 量纲与派生量

时钟同步所界定的是：**一条指令占据多少个周期**。执行时间必须以**机器无关**的方式度量，绝不取宿主的实测耗时，否则同一程序在不同机器上行为不同、回放不可复现。

时间因此退化为计数：

```
f_clock = hz × cycles_per_tick        周期/秒，虚拟时间上唯一的绝对刻度
dt      = 1 / hz                      秒/tick，常数
```

时钟由头段声明（§13.1）：

```
clock   hz                 # tick 率，默认 60
        cycles_per_tick    # 每 tick 的周期预算，默认 1000
```

`hz` 是虚拟时间上**唯一**的绝对刻度。周期表的整体缩放被它吸收：把表内所有周期数同乘一个常数，只要同时调整 `hz`，`dt` 与所有时间轴不变。**只有比例有意义。**

### 6.2 周期计费表

每条指令的周期数**按 opcode 定义**，与操作数的值无关。下表为 v1，归一化基准 `IADD = 1`。

| 指令 | 周期 |
|---|---|
| `FMOV` `IMOV` `FMOVI` `NOP` | 1 |
| `IADD` `ISUB`（基准） | 1 |
| `IMUL` | 3 |
| `I2F` `F2I` | 2 |
| `FADD` `FSUB` | 3 |
| `FMUL` | 4 |
| `FNEG` `FABS` | 1 |
| `FMIN` `FMAX` | 2 |
| `FCLAMP` | 3 |
| `FSQRT` | 12 |
| `FDIV` | 14 |
| `FFRAC` | 6 |
| `FSIN` `FCOS` | 40 |
| `FMADD` | 5 |
| `FLERP` | 8 |
| `FSENSE` `ISENSE` | 1 |
| `FVGET` `IVGET` `FVSET` `IVSET` | 1 |
| `FEXCITE` | 1 |
| `JMP` `IJZ` `IJNZ` | 1 |
| `FLT` `FLE` `FGT` `FGE` `ILT` `ILE` `IGT` `IGE` `IEQ` `INE` | 1 |
| `YIELD` `WAIT` | 2 |
| `HALT` | 1 |

**复合指令按整条计费，不按展开求和。** `FLERP` 是 8，不是 `FSUB + FMUL + FADD` 的 10；`FCLAMP` 是 3，不是 `FMAX + FMIN` 的 4。基础运算名字（`FADD` = 3 等）是**基准锚点**，用于说明比例；每条指令的实际计费以本条为准。

> **规则：** 每条指令的周期数完全由 **opcode** 决定。不得依赖任何寄存器的值、任何内存内容，也不得依赖宿主的实际性能。

特别地，`FSIN`/`FCOS` 的范围规约即使实现为迭代，**迭代次数也必须固定，不得随输入变化**。否则周期数变成数据相关，`WAIT` 的 tick 换算与 `dt` 的语义当场崩掉。

### 6.3 版本化

周期计费表的任何变动都会改变时钟速率与 tick 换算，从而改变已有程序的行为——**即使字节码一个字节没变**。因此：

- 计费表属于**程序语义**，是重放记录的必要组成部分。
- 更改计费表必须提升版本号，并且**不得重定义已发布的表**。
- 与 §4.3 对 `FSIN` 多项式的处理一致：定一次、冻结、带版本。

### 6.4 tick 计数器

- `tick` sensor（§4.7）暴露"已推进的 tick 数"，类型 i32，逐 tick 递增，**二进制补码回绕**（G6）。
- 它是唯一对程序可见的时间索引，也是重放记录的时间基准。
- 因为 `dt` 是常数，`tick × dt` 是确定的虚拟时刻。

### 6.5 tick 周期预算

`cycles_per_tick` 同时是**每 tick 全体任务共享的周期预算**。

- 每个 tick 开始时预算重置为 `cycles_per_tick`。
- 周期消耗在 tick 内跨任务累加。
- 一旦剩余预算为 0，在**执行下一条指令之前**触发超预算 fault：确定性失败，语义同 G12，任务立即终止并被移除，记录 `(task_id, pc, 原因)`，`pc` 指向那条未执行的指令。

**预算必须全局共享。** "帧工作量上界"只有在预算是全局的时才成立——每任务各自一份的话，`N` 个任务就能烧掉 `N × cycles_per_tick`，上界消失。

**这是一条真实的耦合**：一个任务消耗 600 周期，同 tick 内后执行的任务只剩 400。因此"某任务是否超预算 fault"可以依赖同 tick 内其他任务的消耗（§2.4）。重放不受影响：按 `TaskId` 顺序整场重放即可复现。

### 6.6 两层时间模型

真实时间**只存在于 VM 之外**，抖动在这里被吸收：

```
层 1  VM（虚拟时钟）      tick 边界 + dt = 1/hz，全是常数
层 2  host（真实时间）    把真实经过的时间换算成本帧推进几个 tick
层 3  后端（真实时间）    帧内插值、视觉平滑
```

层 2 是唯一读真实时间的地方：

```rust
// host 侧，每显示帧执行一次。不在 VM 内。
accumulator += wall_clock_elapsed_this_frame;   // 真实秒，带抖动
while accumulator >= dt {
    vm.tick(&sensors);        // 每次调用就是一个完整的 VM tick
    accumulator -= dt;
}
// accumulator 的小数余量留在 host，不进入 VM
```

- 一个显示帧可能推进 **0、1 或多次** VM tick。不确定的只是"每帧几步"，每一步的内容完全确定。
- 真实秒被换算成整数个 tick，小数部分丢掉，**余量永不进入 VM**。
- 因此宿主调度抖动影响的是每帧推进的 tick 数量，而不是任何 tick 的内容。

**追赶上限。** 若一帧的真实耗时长期大于 `dt`，追赶会慢于积累，形成 death spiral。工程做法是给每帧的 tick 数设上限（参考值 8）。超过上限时**虚拟时间落后于真实时间**，表现为动画变慢——这不影响 VM 的确定性，只是虚拟时间与真实时间的对齐问题。上限属于层 2 的策略，由 host 决定，本规范只要求它不进入层 1。

### 6.7 挂起时长上界

`WAIT` 的时长不受 fuel 约束：`WAIT 999999999` 只消耗一条指令的 fuel，却能让任务沉睡到热寂。该任务在行为上与 `HALT` 不可区分（不执行、不贡献），因此头段声明 `max_wait`，加载期拒绝超出的 `WAIT`（§10）。缺省值为 **600 虚拟秒**。

单次 `WAIT` 的换算完全落在周期量纲上，不依赖宿主，是确定的：

```
k_cycles = ceil(seconds × f_clock)
k_ticks  = ceil(k_cycles / cycles_per_tick)
```

### 6.8 fuel 与周期的分界

**两套计量互不干涉。**

| | fuel | 周期 |
|---|---|---|
| 量纲 | 指令**条数** | 时钟**周期** |
| 权重 | 全部为 1（§7.2） | 按 opcode（§6.2） |
| 解决的问题 | 逻辑不推进——死循环 | 机器无关的时间度量 + 帧工作量上界 |
| 出口 | fuel 耗尽 fault（§7.3） | 超预算 fault（§6.5） |

**fuel 永远按指令条数等权重 1 计费，不得改成按周期计费。** 否则"循环检测的精确边界"会变成计费表的函数：表一变，同一段字节码会在**不同的 `pc`** 上 fault，从而违反 §7.3。更根本地说，一张只管时间度量的性能表不应成为安全边界——"这段程序需要重写"这个判断不应依赖计费表的标定准确度。

**`WAIT` 为什么不消耗 fuel：** `YIELD` 与 `WAIT` 是任务仅有的两个自愿出口，任何加在它们头上的成本都会惩罚"让出"本身——一个每 tick `YIELD` 一次的常住任务会瞬间烧光预算，从而杀掉 §2.4 承认的合法程序（呼吸、待机摆动）。

顺带一个免费性质：周期消耗完全由 `pc` 轨迹决定，每条指令的周期数有上界，所以单次恢复的周期消耗有上界 `fuel_default × max_cycle_cost`。**fuel 已经免费给出了工作量上界。**

### 6.9 时间意图：开环与闭环

时钟是虚拟的，而肌肉由后端在真实时间里推进。**后端在虚拟时间轴上的时刻不可观测**——时钟只数指令占了多少周期，后端花多少真实时间是后端的事（§9.4）。于是：

> **被控对象什么时候"响应"无法用虚拟时间表达。**
>
> `WAIT 0.1` 推进 6 个 tick，与肌肉是否动到位没有任何关系。它从来不是、也永远不能是"等到某件事发生"。

**闭环反馈必须走 `YIELD`。** 每一个 tick 是一次完整的"激发 → 后端推进 → 观测"：

```
L:  FSENSE  r0, smile        # 观测上一步激发的后果
    FGT     r0, r_thresh, L_done
    YIELD                    # 本 tick 到此为止，让后端推进
    JMP     L                # 下一 tick 重新观测
L_done:
```

| | 表达方式 | 前提 | 典型用途 |
|---|---|---|---|
| **开环定时**（按虚拟时钟排节目） | `WAIT s` | 不依赖被控对象 | 眨眼时长、动作分段、波形相位 |
| **闭环反馈**（等被控对象） | `YIELD` + 条件跳转 | 只需要"后端已推进" | 等笑容到位、等摆动收敛 |

**判据：只要条件里出现了 sensor 的当前值，就必须走 `YIELD`。**

两个必然后果：

1. **反馈必然落后至少一个 tick。** 由 G7（快照在 tick 边界冻结）与 G10（激发值保持）共同保证：一次激发的最早可观测后果出现在下一个 tick。
2. **`WAIT` 不能与轮询混用来表达反馈。** 在"条件未成立"时用 `WAIT` 省开销，等于断言"后端在那么多虚拟时间里一定会完成"——而这个前提在虚拟时间轴上恰好无法表述。

## 7. Fuel 系统

> **实现状态：尚未实现。** 当前行为视为"无限"。但下述**契约已冻结**：fuel 上线后不得改变程序语义，除了那些本来就会耗尽 fuel 的程序。

### 7.1 契约

fuel 是**按任务每次恢复计量的指令预算**。

- 头段声明：全局默认 `fuel_default`，以及可选的单元级覆盖。
- 单位：指令条数。

**为什么按恢复计而不是按生命期计**：待机呼吸是永不终止的循环，按生命期计必然耗尽，但它是完全合法的程序。按恢复计同时保证了**一个贪心任务不会饿死同一 tick 内的其他任务**；每 tick 总工作量的上界是 `任务数 × fuel`。fuel 与周期是两套互不干涉的计量（§6.8）。

### 7.2 消耗规则

- 每条**已执行**的指令消耗 1，包括 `HALT`、`NOP`、`YIELD`、`WAIT`，以及条件成立与否都会执行的跳转指令本身。
- **所有指令等权重 1**，不按 opcode 加权。
- 消耗量必须完全由 `pc` 轨迹决定，与数据无关。

### 7.3 耗尽语义

- 在 fuel 归零后**下一条指令执行之前**触发。
- 确定性 fault，语义同 G12：任务立即终止并被移除，记录 `(task_id, pc, 原因)`。
- 相同输入必须在**同一个 `pc`** 上耗尽。

### 7.4 记录与版本化

- fuel 值属于程序声明，随程序镜像持久化。
- fuel 恒按指令条数等权重 1 计费，因此不存在需要版本化的权重表。
- fuel 耗尽产生的 fault 是**可重放的行为**，不是错误——它和普通 fault 走同一条记录路径。

## 8. 任务模型

### 8.1 任务状态

```rust
pub struct Task {
    pub id:       TaskId,      // 单调递增，决定确定性顺序
    pub layer:    u16,         // 动作声明，VM 只搬运，不解释
    pub pc:       u32,
    pub regs_f:   [f32; 64],
    pub regs_i:   [i32; 64],
    pub vars:     Vars,
    pub values:   Box<[f32]>,  // 长度 = 肌肉数，该任务的当前命令值
    pub set_mask: BitVec,      // 该任务是否曾设定过该肌肉
    pub wake_at:  u64,
    pub status:   Status,      // Running | Halted | Faulted
}
```

`values` + `set_mask` 一起实现"保持"语义（G10）：**值一直保留到被改动，这不是某个机制实现出来的，而是数据结构的性质。**

任务不持有周期计数器：tick 周期预算是每 tick 全局重置的（§6.5）。

### 8.2 生命周期

```
创建 ──▶ Running ──┬── YIELD / WAIT ──▶ 挂起 ──▶ Running
                   ├── HALT ──────────▶ Halted   （动作执行完成，被移除）
                   └── fault ─────────▶ Faulted  （被移除，贡献同时消失）
```

- **创建**：由 host 完成，VM 不提供创建指令。寄存器清零，变量取头段初值，`set_mask` 全零。
- **恢复**：从 `pc` 开始执行，直到挂起 / `HALT` / fault / fuel 或预算耗尽。
- **移除**：`Halted` 与 `Faulted` 的任务在同一 tick 结束时从任务集合中删除。

### 8.3 并发与确定性顺序

多个任务并发运行。**顺序敏感的一切都按任务创建顺序**：

- 任务恢复顺序 = `TaskId` 递增
- 贡献列表排列顺序 = `TaskId` 递增

因此"最后写入获胜"这类顺序敏感的后端策略也是可重放的。**前提是 host 以确定的方式创建任务**——这是一条必须遵守的约定。

### 8.4 tick 结构

```rust
fn tick(&mut self, sensors: &Sensors) {
    // dt 不由外部提供：clock 来自头段声明，dt = 1 / hz，是常数（§6.1）。
    let dt = 1.0 / f32::from(self.clock.hz);

    // 分字段解构：tasks / snapshot / scratch / backend 是不同字段，
    // 借用检查器允许同时 &snapshot 与 &mut tasks，不需要 unsafe 也不需要 RefCell。
    let Self { tasks, snapshot, scratch, backend, muscle_count, now, .. } = self;

    // 1. 采样 sensor，整 tick 冻结（G7）
    sample_into(snapshot, sensors);

    // 2. 重置本 tick 的周期预算（§6.5）
    let mut budget = self.clock.cycles_per_tick;

    // 3. 按创建顺序恢复到期的任务
    for t in tasks.iter_mut() {
        if t.wake_at <= *now {
            resume(t, snapshot, &mut budget);  // 推进到挂起 / HALT / fault / fuel 或预算耗尽
        }
    }
    tasks.retain(|t| t.status == Status::Running);

    // 4. 逐肌肉收集贡献，原样交给后端
    for m in 0..*muscle_count {
        scratch.clear();                     // 复用缓冲区，不是每 tick 新建
        for t in tasks.iter() {
            if t.set_mask.test(m) {
                scratch.push(Contribution {
                    value: t.values[m],
                    layer: t.layer,
                    task:  t.id,
                });
            }
        }
        backend.excite(m, scratch, dt);
    }

    *now += 1;                               // tick 计数器（§6.4）
}
```

`scratch` 必须复用——**每肌肉每 tick 新建一个 `Vec` 会是唯一的热路径分配。**

### 8.5 没有的东西

VM 里没有：调度器、任务树、`spawn`、`await`、fork/join、优先级队列、图层合成、命令缓冲区、数值净化。

动作的选择、创建、销毁、串联、优先级策略，全部在 VM 之上的层。

## 9. 后端接口（Rust）

### 9.1 边界是参数向量

VM 与后端之间**只有激发值和外加的来源信息**。后端持有全部被控对象状态、全部约束、全部合成逻辑。

### 9.2 后端 trait

```rust
pub trait Backend {
    /// 每个肌肉每 tick 调用一次，传入该肌肉本 tick 收到的全部贡献。
    /// 调用顺序按肌肉下标，贡献顺序按 TaskId。
    fn excite(&mut self, muscle: MuscleId, contributions: &[Contribution], dt: f32);
}

pub struct Contribution {
    pub value: f32,
    pub layer: u16,     // 动作声明的层；VM 不解释，只搬运
    pub task:  TaskId,
}
```

**冲突裁决完全在这里发生。** "A 覆盖 B"、"新任务压过旧任务"、"取最小值"、"加权和"——都由后端实现。

VM 之所以要搬运 `layer` 和 `task`，是因为**后端需要来源信息才能实现任何优先级策略**。这不是 VM 理解肌肉语义，只是把原料交齐。

### 9.3 后端辅助库

以下都是**便利设施，不是 VM 的一部分**，后端可以完全不用：

| 设施 | 说明 |
|---|---|
| 约束求解器 | XPBD / 顺序冲量等，供后端在 `excite` 之后调用 |
| 合成策略 | 覆盖栈、加法层、min/max 图层等标准实现 |
| 净化助手 | 范围钳制、NaN/Inf 拒绝的标准写法 |
| 帧内插值 | 两次 tick 之间的 `FLERP` 平滑 |

后端**可以**只实现一个 `combine` 帮助函数就覆盖绝大多数皮套需求，但这是库的选择，不是 VM 的约束。

### 9.4 确定性契约

> **VM 保证激发流确定；后端是否确定是后端的性质。**

三层时间模型（§6.6）把时间也划在这条线两侧：

- **VM 侧（层 1）**：tick 边界与 `dt` 都是虚拟的、常数化的，宿主提供不了时间，因此 VM 的激发流在所有平台上逐位一致。
- **host 侧（层 2）**：真实时间只用来决定本帧推进几次 tick。抖动改变的是每帧推进的 tick 数量，不改变任何 tick 内部的语义。
- **后端侧（层 3）**：真实时间用于帧内插值与视觉平滑，不反馈进 VM。

#### 9.4.1 数学归属

**ISA 数学指令由本规范唯一定义，后端不得替换其实现。** 原因有两条：

1. **指令语义全局唯一。** `FSIN`/`FCOS` 跨平台逐位一致是已冻结的承诺（§4.3）。VM 里跑的 `FSIN` 属于指令语义，不是某个模块的实现细节。
2. **周期计费表与它绑定。** §6.2 的表是离线预标定的，标定对象正是那个唯一实现。实现一换，`FSIN = 40` 就失去指称对象。

**后端肌肉自己的数学则完全自由。** 动力学、约束求解、摆动、插值——用哪个 `sin`、怎么近似、精度多少，本规范一概不管。这不是放松要求，而是程序走 `YIELD` 调度的直接后果：

- 程序在 tick 之间的行为只依赖 `(自身状态, sensor 快照)`（§2.4）。
- VM 的下一条指令只由程序和那份快照决定（G7、G8）。
- 因此**后端算出的任何数字都无法改变程序的指令序列**，也就无法改变周期消耗、无法触及 §6.2 的表。它唯一能影响的是下一 tick 的 sensor 值——而在 VM 看来那只是一个输入。

**代价只落在姿态层面。** 如果 `sin` 在不同平台上差最后几位，**姿态回放**会漂移，**激发流回放不会**。要姿态级可重放，后端自己钉住数学版本。

#### 9.4.2 后端侧约定

后端自身的确定性只能靠约定：

1. **使用确定性数学库**，不要直接调平台 libm——`sin` 的最后几位在不同平台/版本上会差。
2. **不要依赖 FMA 收缩**。Rust 默认不做，但那是编译器行为，不是能声明的契约。
3. **不要引入线程、时钟、哈希表迭代顺序**等非确定来源。

工程措施：

- 在 CI 里加浮点契约测试：对若干组输入断言 `a*b+c` 未被融合、`sin` 的位模式与参考值一致。
- **把后端库的内容哈希写进重放记录**。这不能防止漂移，但能让"这份回放是用哪个版本的动力学产生的"变成可查的事实。
- **插值不得反馈进 VM。** 插值只用于出画面；一旦把插值后的值写回任何 VM 可见的状态，层 3 就污染了层 1。
- 后端必须实现**固定步进**：`excite` 拿到的是常数 `dt`，因此后端不能假设"两次调用之间真实经过了 `dt` 秒"。

### 9.5 信任模型

**后端是可信的原生代码。** 它没有沙箱，能读文件、起线程、死循环。

这是一条**显式前提**，不是隐含假设。它成立的理由是：后端随 rig 一起分发，作者就是 rig 的作者，和 VM 里跑的、可能由 AI 生成或从外部获得的字节码处于完全不同的信任层级。

如果将来需要从**不可信来源**分发 rig，这个决定会反过来——那时需要的正是沙箱，而字节码后端是免费的沙箱。届时可选的路线是：rig 只分发**参数**，动力学来自经过审计的内置后端库。

## 10. 加载期验证清单

全部为 O(n) 一次扫描，运行期零成本：

1. 所有 sensor id 在范围内，且类型与 `FSENSE`/`ISENSE` 匹配。
2. 所有 var id 在范围内，且类型与 `FVGET`/`IVGET`/`FVSET`/`IVSET` 匹配。
3. `FEXCITE` 的肌肉 id 合法。
4. 跳转目标在本单元 `[0, code_len]` 内（§5.3）。
5. 所有 opcode 属于已定义指令；保留 opcode 一律拒绝。
6. **未使用的字段必须为 0**——包括无 `imm` 语义的指令的 `imm`，以及该指令不使用的 `rd`/`ra`/`rb`/`rc`。这使已 bind 的镜像具有**唯一规范形式**，可安全用于哈希、缓存键与版本比对。
7. `WAIT` 的 `imm` 必须是非负有限 f32，且不超过头段 `max_wait`（§6.7）。
8. 执行单元以 `HALT` 结尾（不足时由 binder 补齐）。
9. 头段 `clock` 的 `hz`、`cycles_per_tick` 必须是正数；缺省时取默认值。
10. `cycles_per_tick` 必须不小于 §6.2 表中最贵指令的周期数——否则任何含该指令的 tick 都必然超预算。

## 11. 命名规范与 lint

> **前缀 = 源操作数所属的族。**

| 指令 | 源 | 前缀 |
|---|---|---|
| `FADD rd, ra, rb` | 浮点寄存器 | `F` |
| `IADD` | 整数寄存器 | `I` |
| `FMOVI rd, imm` | 浮点立即数 | `F` |
| `I2F rd, ra` | **整数**寄存器（目的才是浮点） | `I` |
| `F2I rd, ra` | **浮点**寄存器 | `F` |
| `FEXCITE imm, ra` | 浮点寄存器 | `F` |
| `FSENSE rd, imm` | sensor（f32） | `F` |
| `IJZ ra, imm` | 整数寄存器 | `I` |
| `FLT ra, rb, imm` | 浮点寄存器 | `F` |
| `JMP`/`YIELD`/`WAIT`/`HALT`/`NOP` | 无寄存器源操作数 | 无 |

规律写成"**源**的族"而非"**目的**的族"，`I2F`/`F2I` 就自动合规，不需要例外。

**CI lint：**

```
每条助记符必须匹配   ^(F|I)[A-Z0-9]+$
例外且仅例外：        JMP, YIELD, WAIT, HALT, NOP   （无寄存器源操作数）
```

**第二条规则（防的是 bug，不是风格）：**

> 任何指令，只要其寄存器操作数的文件**不是单靠 opcode 就能确定的**，必须拆成两条带前缀的指令。

`IN rd, imm` 就是因为违反这条而被拆成 `FSENSE`/`ISENSE`——目标寄存器在 `f` 还是 `i` 取决于 sensor 的头段类型，解码器无法只看 opcode 决定访问哪个数组。

## 12. 刻意省略的特性

| 未实现 | 理由 | 将来补的代价 |
|---|---|---|
| 全局变量 | 并发下会引入"裁决全局写入"的问题，而它没有像肌肉那样的自然归宿 | 长期状态改用**永不 HALT 的任务**；不建议补 |
| 调度器 / 动作选择 | 纯上层关注点，VM 不该知道 | 不需要 |
| `spawn` / `await` / fork-join | 动作是原子的，不调用动作 | 纯增量 |
| 冲突裁决 / 图层合成 | 属于后端语义；VM 内置枚举等于把皮套知识放回 VM | 不需要 |
| 数值钳制 / 净化 | 属于后端；辅助库提供标准实现 | 不需要 |
| 约束求解器 | 属于后端辅助库 | 不需要 |
| 命令缓冲区 | "保持"语义取代了"每 tick 合成" | 不需要 |
| `CALL` / `RET` | 任务已是独立执行单元；子程序可后续增量添加 | 增量 |
| 常量池 | 定长 8 字节格式中 `imm` 是白送的 | 不需要 |
| 索引化读取（`INX`） | 会在热路径引入"浮点索引 → 整数 → 边界检查" | 增量 |
| 批量数据段 | 样条关键帧表之类属于 data section | 增量，需独立 bind 期重定位表 |
| `FFMA`（融合乘加） | 需要宿主硬件 FMA 才能位精确 | 增量 |
| 浮点相等比较（`FEQ`） | 故意没有：浮点 `==` 是 bug 温床，NaN 还让它不可全序 | 用 `FSUB + FABS + FLT` 配容差 |
| `WAITUNTIL`（挂起直到条件成立） | 条件只能靠 sensor 观测，而 sensor 只在 tick 边界更新（G7）；`YIELD` + 条件跳转 + `JMP` 已完整表达（§6.9） | 不需要；真需要时是伪指令层的事 |

### 12.1 浮点容差比较

`FSUB + FABS + FLT` 在任何输入下都不会算错：

- **相近浮点相减是精确的**（Sterbenz 引理：同号且 `y/2 ≤ x ≤ 2y` 时 `x - y` 精确可表示）。灾难性抵消说的是结果的**相对**精度，而我们要问的正是"这两个已存值差多远"。
- 差值下溢到 0 或非规格化 ⇒ 本来就该判"近"；溢出到 ±Inf ⇒ 本来就该判"远"；NaN ⇒ 比较为假，与 G5 一致。

真正会出问题的是另外两件事：

1. **容差小于 ULP ⇒ 静默退化为"精确相等"**。例如 f32 在 `1024.0` 附近 ULP 为 `1.22e-4`，取 `eps = 1e-5` 时该测试恰好等价于 `a == b`。经验法则：`eps ≳ 8 × ULP(最大量级)`。
2. **忘了 `FABS`** ⇒ `a - b < eps` 会被很负的差满足，是静默 bug。

正确写法：

```
FSUB t, ra, rb
FABS t, t
FGE  t, r_eps, L_skip      # 或 FLT 得到相反极性，不需要额外 JMP
```

另外，单阈值会在阈值附近**逐帧抖动**——这比 ULP 级误差严重得多。状态机应使用**滞回带**（进入用 `r_on`、退出用 `r_off`）。

最后：**需要精确比较的量（计时器、计数器、状态号、帧号）本来就该放在 `i` 寄存器**，`IEQ`/`INE` 是精确的。缺 `FEQ` 是一种设计压力，把离散量推向正确的域。

## 13. 头段与 bind

### 13.1 头段声明的内容

| 声明 | 作用 |
|---|---|
| `muscle` | 名字。**仅此而已**——VM 不需要知道肌肉的任何语义 |
| `group` | 名字 → 肌肉列表；bind 期在 `FEXCITE` 处**展开**，运行期无"组"概念 |
| `sensor` | 名字 → 来源绑定（肌肉当前值 / 后端可观测量 / 内置 dt、tick），带类型 |
| `var` | 名字、类型（f32/i32）、初值 |
| `layer` | 该动作声明的层号，VM 只搬运（§9.2） |
| `fuel` | `fuel_default` 与单元级覆盖（§7） |
| `clock` | `hz` 与 `cycles_per_tick`（§6.1）。缺省时取默认值 |
| `max_wait` | 单次 `WAIT` 的时长上界（§6.7）。缺省 600 虚拟秒 |

肌肉在头段里只是一个名字，因为**它的语义完全在后端**。

### 13.2 bind 在加载期做的事

1. 解析头段，分配任务变量、传感器数组、命令值向量。
2. 把逻辑 id（muscle / sensor / var）解析成物理下标并内联进 `imm`。
3. 展开 `group`。
4. 执行 §10 的全部校验。
5. 产出**冻结的**可执行镜像：`Box<[u64]>` 指令流 + 元数据。

### 13.3 名字对不上怎么办

程序引用肌肉名，后端注册肌肉实现，bind 时匹配。缺失时有两种策略：

- **硬错误**：简单，但程序无法跨 rig 复用。
- **绑到 VOID**（推荐）：激发被静默吸收（读恒 0）。保留跨 rig 可移植性——为 100 个参数的模型写的动作放到 30 个参数的模型上能安静降级执行。

Live2D 模型之间的参数集差异本来就大（有的有身体角度、有的没有），硬错误会让动作完全无法复用。

## 附录 B：寄存器分配建议（面向生成器）

- 活跃值通常不超过 20 个；64 个寄存器对代码生成足够宽裕。分配器应优先简单而非最优。
- 寄存器**跨挂起存活**，但**不跨任务**，所以不存在 callee-saved 约定，也没有寄存器窗口。
- 跨动作存活的状态溢出到**永不 `HALT` 的任务**，不是变量。
- 常量一律用 `FMOVI` 在循环外物化一次并复用；`0.0` 直接用 `f0`。
- 浮点判真用 `FGT ra, f0, L`；判负用 `FLT ra, f0, L`。
- 周期性行为写成 `WAIT` 循环，不要用一长串展开的关键帧。
